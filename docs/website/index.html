LunaDB 0.0.1

Setup

LunaDB é um banco de documentos JSON/MessagePack autocontido, exposto como API HTTP. Cada tabela é um arquivo em disco, registros podem ser validados por um schema opcional, campos sensíveis são cifrados em repouso e o acesso é controlado por roles, grants por banco e API keys.

Primeiro acesso

A partir daí, criar um banco, uma tabela e o primeiro registro:

curl -s -X POST $BASE/dbs -H "authorization: Bearer $KEY" \
  -H 'content-type: application/json' -d '{"name":"app"}'

curl -s -X POST $BASE/dbs/app/tables -H "authorization: Bearer $KEY" \
  -H 'content-type: application/json' -d '{"name":"notas"}'

curl -s -X POST $BASE/dbs/app/tables/notas/records -H "authorization: Bearer $KEY" \
  -H 'content-type: application/json' -d '{"titulo":"primeira nota"}'

A senha padrão do root é changeme. Troque-a na config antes de expor o servidor; no primeiro boot o texto puro do config.toml é substituído por um hash argon2id. Trocar a senha revoga todas as API keys ativas do usuário.

Configuração

O gerador interativo make luna-setup pergunta host, port, caminho e formato do storage, limite de corpo, timeout, usuário e senha do root e as opções de log. Enter aceita o default mostrado entre colchetes; Enter na senha gera uma aleatória, impressa uma única vez. O arquivo é gravado com modo 600 e não sobrescreve uma config existente sem confirmação (use --force).

make luna-setup                                  # grava ~/.lunadb/config.toml
make luna-setup ARGS="--config /tmp/app/config.toml"
make luna-setup ARGS="--force"

Autenticação

Todas as rotas (exceto GET /health e POST /auth/login) exigem um header Bearer. As keys pertencem a um usuário e podem ser criadas e revogadas individualmente; o plaintext só é retornado na criação e no login:

Authorization: Bearer luna_<64 hex>

API HTTP

DSL de schema

{
  "strict": true,
  "unique": ["cpf", ["tenant_id", "email"]],
  "fields": {
    "email":      {"type":"string","required":true,"pattern":".+@.+\\..+","unique":true},
    "senha":      {"type":"string","required":true,"encrypted":true,"min_length":8},
    "idade":      {"type":"int","min":0,"max":150},
    "ativo":      {"type":"bool","default":true},
    "tags":       {"type":"array","items":{"type":"string"}},
    "endereco":   {"type":"object","fields":{"cidade":{"type":"string","required":true}}},
    "external_id":{"type":"uuid"},
    "nascimento": {"type":"date"},
    "criado":     {"type":"datetime","auto":"created_at"},
    "atualizado": {"type":"datetime","auto":"updated_at"},
    "meta":       {"type":"any"}
  }
}
  • Tipos: string, int, float, bool, datetime (RFC3339), date (YYYY-MM-DD), uuid, object, array, any.
  • Propriedades de campo: required, nullable, default, unique e encrypted (ambos só no topo), min/max, min_length/max_length, pattern, enum, items, fields, auto.
  • encrypted: valor cifrado em disco (AES-256-GCM) e decifrado de forma transparente na API; continua filtrável, mas não pode ser unique.
  • strict: rejeita campos não declarados no registro.

Migração incremental (PATCH .../schema)

{
  "add": {"telefone": {"type": "string", "required": false}},
  "update": {"email": {"required": true, "max_length": 120}},
  "remove": ["campo_antigo"],
  "unique_add": [["tenant_id", "email"]],
  "unique_remove": ["cpf"],
  "strict": true
}
  • add: insere campos novos; erro 400 se o campo já existir (use update).
  • update: merge raso nas propriedades do campo; null limpa a propriedade; erro 400 se não existir.
  • remove: remove campos; erro 400 se não existir. Campos removidos em modo não-strict permanecem nos registros (nenhum dado é apagado).
  • unique_add / unique_remove: chave simples ("email") ou composta (["a","b"]).
  • Registros inválidos após a operação → 409 com os ids; ?force=true aplica mesmo assim.

Paginação por cursor

# primeira página
curl -s "$BASE/dbs/app/tables/notas/records?limit=50" -H "authorization: Bearer $KEY"
# -> {"total":1200,...,"next_cursor":"eyJrIjpbLi4uXX0"}

# próxima página
curl -s "$BASE/dbs/app/tables/notas/records?limit=50&cursor=eyJrIjpbLi4uXX0" \
  -H "authorization: Bearer $KEY"
  • O cursor é uma posição keyset em base64url, não um offset; uma varredura nunca pula nem repete registro, mesmo com escritas concorrentes.
  • _id é sempre a última chave de ordenação (desempate). Sem sort, ordem por _id crescente.
  • next_cursor só vem enquanto houver mais páginas; a última (curta) o omite.
  • Enviar cursor e offset juntos usa o cursor e ignora o offset; cursor malformado ou incompatível com o sort atual → 400.

Query

{
  "filter": {"$or": [{"idade": {"$gte": 18}}, {"tags": {"$contains": "vip"}}],
             "endereco.cidade": "SP"},
  "sort": ["-idade", {"field": "nome", "dir": "asc"}],
  "fields": ["nome", "endereco.cidade"],
  "limit": 20,
  "offset": 0,
  "cursor": "eyJrIjpbLi4uXX0"
}
  • Operadores: $eq, $ne, $gt, $gte, $lt, $lte, $in, $nin, $exists, $contains (substring em string, pertence em array), $starts_with, $ends_with, $regex, $and, $or, $not. Igualdade é implícita: {"tenant": "t1"}.
  • Caminhos: a.b (objetos) e tags.0 (índice de array); filtro por _id funciona.
  • sort: "campo", "-campo" (desc) ou {"field","dir"}; nulos e ausentes sempre por último.
  • fields: projeção (aceita caminhos aninhados); _id sempre incluído. Campos encrypted podem ser filtrados (decifra em memória).
  • Operador, filtro ou cursor inválido → 400; campo desconhecido no corpo → 422.

Agregações

{
  "filter": {"ativo": true},
  "group_by": ["cidade"],
  "aggregates": {
    "total":  {"op": "count"},
    "receita": {"op": "sum", "field": "valor"},
    "ticket":  {"op": "avg", "field": "valor"},
    "menor":   {"op": "min", "field": "valor"},
    "maior":   {"op": "max", "field": "valor"}
  },
  "limit": 50
}

Retorna groups, cada um com key (valores de group_by), count e o resultado de cada agregado. Operações: count, sum, avg, min, max (as numéricas exigem field). Grupos são ordenados pela chave.

Servidor

lunadb serve     # sobe a API; Ctrl+C / SIGTERM encerram de forma graciosa

Para a configuração interativa, veja (make luna-setup).

API keys (não-interativo)

export LUNADB_API_KEY=luna_...    # key de um admin

lunadb apikey create bob --name ci      # imprime a key nova (uma única vez)
lunadb apikey list bob                  # JSON das keys do bob
lunadb apikey list                      # JSON das próprias keys
lunadb apikey revoke bob luna_abc123    # por id ou prefixo

A saída de create é apenas a key (para $() em scripts); list e revoke retornam JSON.

Migração de formato (offline)

Converte todas as tabelas entre MessagePack (default) e JSON. Exige servidor parado (detecta via infra/status.json e pid; use --force para ignorar).

lunadb migrate --to json
lunadb migrate --to msgpack --force

Shell interativo

lunadb shell
lunadb shell --server http://127.0.0.1:7700 --key luna_...
  • Histórico persistido em ~/.lunadb/infra/shell_history.
  • login sem senha usa prompt oculto.
  • JSON sempre entre aspas simples (o parser remove as duplas): add app notas '{"titulo":"oi"}'.
  • exit, quit ou Ctrl+D encerram; erros aparecem como erro: HTTP 403: ... sem acabar com a sessão.

SDK Python (lunapy)

Cliente oficial sem dependências externas (apenas stdlib), que fala com a API por HTTP. Todos os métodos levantam exceções tipadas, e os atalhos novos (handles, queries encadeadas e Record) não substituem a API original.

Instalação

pip install -e lunapy          # a partir deste repositório
pip install -e "lunapy[dev]"   # com pytest

Criando o cliente

from lunapy import LunaClient, connect

# a partir do config.toml (~/.lunadb ou LUNADB_CONFIG)
client = LunaClient.from_config()

# ou explícito; as envs LUNADB_URL / LUNADB_API_KEY também são aceitas
client = LunaClient(base_url="http://127.0.0.1:7700", api_key="luna_...")

# cria o cliente e faz login em um passo; funciona como context manager
with connect(base_url="http://127.0.0.1:7700",
             username="root", password="changeme") as client:
    print(client.me().username)

# login avulso: rotaciona a chave "login" e guarda no cliente
user = client.login("root", "changeme")
print(user.username, user.role)

connect() é equivalente a LunaClient.connect(...); sem argumentos usa LUNADB_URL/LUNADB_API_KEY e o host padrão.

Handles (menos repetição)

client.db() e client.table() devolvem handles leves que guardam o banco/tabela. Todos os métodos de baixo nível continuam disponíveis e iguais.

app = client.db("app")             # ou client["app"]
users = app.create_table("users")  # -> Table
users = app["users"]               # handle para tabela existente

users.create(name="Ana", age=30)   # kwargs viram campos do registro
record = users.first(name="Ana")   # -> Record
print(record.name, record["age"])

users.update(record["_id"], age=31)
users.replace(record["_id"], name="Ana", age=32)
users.delete(record["_id"])

for person in users:               # paginação por cursor por baixo
    print(person.name)

len(users)                         # users.count()
record["_id"] in users             # checa existência
users[record["_id"]]               # users.get(id)

Record é subclasse de dict: record["nome"] continua funcionando e record.nome é um atalho. Métodos de dict têm precedência em nomes conflitantes, então use record["items"] para um campo chamado items.

Queries encadeadas

for user in users.where(idade__gte=18).sort("-idade").select("nome", "idade").limit(50):
    print(user.nome)

users.where(tags__contains="vip").count()
users.where(cidade="SP").first()       # -> Record | None
users.where(idade__gte=18).ids()       # -> lista de _id
users.where(idade__gte=18).one()       # LunaNotFoundError se vazio

Operadores por keyword: eq, ne, gt, gte, lt, lte, in, nin, contains, startswith, ends_with, regex e exists. Para $and/$or/$not ou nomes com ponto ("endereco.cidade"), passe filter={...} explicitamente.

Databases, tabelas e schema

client.list_dbs()          # -> list[DbMeta]
client.create_db("app")    # -> DbMeta (admin)
client.get_db("app")
client.delete_db("app")
from lunapy import TableSchema, Field

schema = TableSchema.of(
    tenant=Field.string(required=True),
    email=Field.string(required=True, unique=True, pattern=r".+@.+\..+"),
    senha=Field.string(required=True, encrypted=True, min_length=8),
    idade=Field.int(min=0, max=150),
    ativo=Field.bool(default=True),
    tags=Field.array(items="string"),
    criado=Field.datetime(auto="created_at"),
)

# TableSchema(unique="cpf") também vale; strings e dicts crus são aceitos
client.create_table("app", "users", schema=schema)      # schema opcional
client.list_tables("app")                               # -> list[str]
client.get_schema("app", "users")                       # -> TableSchema
client.set_schema("app", "users", schema, force=False)  # -> TableSchema
client.delete_schema("app", "users")
client.delete_table("app", "users")

Atalhos: Field.string, Field.int, Field.bool, Field.array, Field.datetime, Field.uuid, Field.object e Field.any. Field("bool"), FieldType e AutoField continuam aceitos; o schema também pode ser passado como dict cru.

Migração incremental

Funciona também quando a tabela ainda não tem schema (cria do zero):

# patch genérico (mesmo corpo da API PATCH)
client.patch_schema("app", "users", {"add": {"tel": {"type": "string"}}, "strict": False})

# atalhos no cliente ou no handle da tabela
users = client.table("app", "users")
users.add_fields({"tel": Field.string(default="")})
users.update_field("email", {"required": True, "max": None}, force=True)
users.remove_fields("tel", "campo_antigo")
users.add_unique("cpf")                    # ou ("tenant", "email")
users.remove_unique("cpf", force=True)
  • add_schema_fields aceita Field ou dict; update_schema_field faz merge e None limpa a propriedade.
  • force=True aplica mesmo com registros inválidos; sem ele, violações levantam LunaSchemaRejectedError (com .records).
  • Operações inválidas → LunaBadRequestError. TableSchema.to_dict()/from_dict() serializam para o formato da API; dicts crus também são aceitos em create_table/set_schema.

Query e agregações

from lunapy import Sort

result = client.query("app", "users",
    filter={"$or": [{"idade": {"$gte": 18}}, {"tags": {"$contains": "vip"}}],
            "endereco.cidade": "SP"},
    sort=[Sort("idade", "desc"), "-nome"],   # Sort, dict, tupla ou "-campo"
    fields=["nome", "endereco.cidade"],
    limit=20, offset=0)
result.total; result.count; result.records
result.first                              # Record | None

# valores únicos também funcionam: sort="-idade", fields="nome"
# e o builder encadeado é equivalente a query():
result = users.where(idade__gte=18).sort("-idade").select("nome").limit(20).result()

groups = client.aggregate("app", "users",
    group_by="cidade",                     # ou by="cidade" no handle
    total="count", receita="sum:valor",
    ticket={"op": "avg", "field": "valor"},
    filter={"ativo": True})
# -> [Record(key={"cidade": "SP"}, count=2, ...), ...]
groups[0].key.cidade

Layout em disco

Tudo fica sob storage.path da config (~/.lunadb por padrão):

~/.lunadb/
├── config.toml              # configuração de server, storage, root e log (modo 600)
├── meta/
│   ├── users.json           # usuários, hashes de senha e de API key
│   ├── roles.json
│   ├── dbs.json
│   └── master.key           # chave mestra de criptografia (modo 600)
├── dbs/
│   └── <db>/
│       └── <tabela>.msgpack # um arquivo por tabela (ou .json)
└── infra/
    ├── status.json          # pid/porta/versão do servidor em execução
    ├── shell_history
    └── logs/
        └── lunadb.log.*     # logs rotacionados

meta/master.key deriva as chaves de criptografia por banco. Se ela for perdida, todo campo encrypted fica ilegível; não é derivada de nada e não há como recuperá-la. meta/users.json guarda os hashes argon2id de senhas e API keys: perdê-lo significa perder todas as credenciais, mas não os dados.

Backup

Não há backup embutido. O backup seguro é uma cópia do diretório de storage feita com o servidor parado, para que nenhuma tabela esteja no meio de uma escrita (as escritas são atômicas, mas uma cópia com o servidor rodando pode pegar uma tabela entre duas mudanças):

# pare o servidor antes (Ctrl+C ou SIGTERM), depois:
tar czf lunadb-backup-$(date +%F).tar.gz -C ~ .lunadb

A chave mestra faz parte do backup e é necessária para ler campos criptografados. Guarde uma cópia dela em local separado; manter a única cópia junto dos dados anula o propósito dela.

Capacidade e limitações conhecidas

O LunaDB guarda um arquivo por tabela e mantém a tabela inteira em memória durante a requisição: uma escrita de registro regrava a tabela inteira (inserção numa tabela de 100 mil registros codifica e faz fsync de todos os 100 mil). Escritas na mesma tabela são serializadas; em tabelas diferentes rodam em paralelo. Índices unique são reconstruídos a cada escrita. Leituras decodificam a tabela inteira antes de filtrar — limit/cursor limitam a resposta, não o trabalho feito.

Tamanho da tabelaComportamento
até ~10 mil registrosconfortável para uso interativo
~10 mil a 100 milcada escrita recodifica o arquivo; agrupe o trabalho em menos requisições maiores
acima de ~100 milnão recomendado; divida os dados em várias tabelas

Não há transações multi-tabela nem índices secundários além de unique — consistência entre tabelas é responsabilidade do cliente. Pré-1.0, trate os números como orientação e não como contrato; meça com o tamanho real dos seus registros.

Logs

[logging]
level    = "info"      # trace | debug | info | warn | error
console  = true        # também escreve no stdout
file     = true        # escreve em infra/logs/
rotation = "daily"     # never | hourly | daily
max_files = 7          # quantos arquivos rotacionados manter

RUST_LOG sobrepõe o nível quando definido, por exemplo RUST_LOG=lunadb=debug lunadb serve. Ao depurar, procure por dois tipos de linha:

  • lunadb::ops: uma entrada por operação, com op, user, db, table e um count/id. Busque por grep 'op="create_record"' lunadb.log.
  • http_request: method, uri, status e latency_ms; erros de cliente em warn, de servidor em error.

Valores sensíveis nunca são logados: senhas, API keys e campos criptografados permanecem cifrados até no arquivo da tabela.

Problemas comuns

error: api key missing or invalid (401)

A chave está ausente, revogada ou pertence a um login rotacionado: o POST /auth/login rotaciona apenas a key chamada login — keys criadas com lunadb apikey create continuam válidas até revogação. Se você trocou a senha, todas as chaves do usuário foram revogadas; logue de novo.

too many attempts; try again in Ns (429)

Após 5 falhas consecutivas para o mesmo usuário, o login fica bloqueado por 60 segundos. Um login bem-sucedido zera o contador. O bloqueio é por usuário: outra conta não é afetada.

no access to db '<nome>' (403)

O usuário não tem grant que cubra esse banco. O nível efetivo é o máximo entre os grants do usuário e as permissões da role, com * valendo para qualquer banco. Confira com GET /me e GET /roles.

option 'admin' required ao excluir um banco

Só um admin (ou um grant de admin naquele banco) pode excluí-lo; admin é estritamente mais forte que write.

schema rejected by existing records (409)

A mudança de schema invalidaria registros; a resposta lista ids e campos problemáticos. Corrija os registros antes ou repita com force=true para manter os inválidos como estão, por exemplo schema set app usuarios '<json>' --force.

failed to decrypt field '<nome>' (500)

O valor armazenado não decifra com a chave mestra atual: LUNADB_MASTER_KEY diferente, arquivo substituído ou chave movida entre bancos. Os dados não são recuperáveis sem a chave original; restaure meta/master.key do backup (não apague o campo, para não perder dados que a chave restaurada ainda leria).

server appears to be running no lunadb migrate

O migrate reescreve todos os arquivos de tabela e se recusa a rodar com o servidor no ar. Pare-o, ou passe --force se tiver certeza. A checagem confirma que o pid de infra/status.json ainda está vivo, então um resíduo de um servidor que caiu não bloqueia.

O servidor não sobe

os error 99: server.host aponta para um endereço que não existe nesta máquina (use 127.0.0.1 ou 0.0.0.0). Address already in use: outra porta ocupada, verifique ss -ltnp | grep 7700. failed to read master key: storage errado ou incompleto; rode lunadb init.

Arquivo de tabela parece corrompido

As escritas são atômicas (arquivo temporário + rename), então um arquivo pela metade é improvável. Se uma tabela não parseia, inspecione o arquivo direto: .msgpack é MessagePack e .json é JSON indentado. Restaure só aquele arquivo de um backup com o servidor parado.

Atualização de versão

  1. Pare o servidor e faça backup (incluindo meta/master.key).
  2. Compile ou instale o binário novo.
  3. Apague o infra/status.json antigo se estiver obsoleto; ele é recriado na subida.
  4. Suba o servidor, confira o GET /health, faça login e leia uma tabela.

Não há migração automática do layout de storage além do lunadb migrate, que apenas converte tabelas entre JSON e MessagePack.
